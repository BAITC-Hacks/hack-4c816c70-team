## Исправления по коду

### P2 Claude 2 Повторно проверять вручную назначенный район перед добавлением

Файл: `features/planner/Planner.tsx`, строки 80–95. `pendingDistrictFor` возвращает любое сохранённое локальное значение без проверки вновь возникшего конфликта; `handleAdd` проверяет доступность мероприятия в целом, но не конкретного назначения.

Воспроизведение по коду:

1. В ещё не добавленной карточке M7 вручную выбрать Нуру.
2. Добавить M4 в Нуру.
3. Вернуться к M7: локальное назначение всё ещё Нура; `getAddAvailability` возвращает available, поскольку другие районы доступны.
4. Нажать добавление M7 — набор получает конфликтующие M4/M7 в Нуре.

Проверено на скомпилированных функциях: доступность available, getDistrictConflicts возвращает конфликт с M4, а validateDraft добавленного набора возвращает incompatible. Оценка такого набора корректно блокируется, поэтому расчёт не повреждается. Но утверждение отчёта «районный конфликт через UI создать нельзя» неверно.

Исправление: повторно проверять текущий pendingDistrictId перед добавлением и синхронизировать доступность кнопки с этим назначением. Показывать причину и оставлять выбор другого района доступным. Добавить регрессионный сценарий со сменой choices после ручного выбора района.

### P2 GPT Основная область и фокус при смене шага

Файлы: `features/simulator/Simulator.tsx`, строки 25–27; `features/results/Results.tsx`, строка 11. Обзор и Planner рендерятся как section без main; Planner начинает заголовки с h2. Заголовок результата имеет tabIndex=-1, но код не переводит на него фокус. После отправки сфокусированная кнопка исчезает, новый результат не получает фокус.

Исправление в своей области: обеспечить один main на каждом шаге без вложенных main, понятный главный заголовок и перевод фокуса при переходе к результату. Использовать локальный ref/effect либо общий механизм переходов. Проверить клавиатурой возврат к плану и новый результат. Изменение корневого тега или заголовка Planner при необходимости согласовать с Claude 2.
