## Порядок реализации

1. Проверь npm ci, текущие lint и build. Добавь typecheck script с генерацией Next types при необходимости. Сохрани установленный стек; не обновляй версии ради обновления.
2. Подготовь Simulator: единый reducer, active step, scenario load state, choices, selectedDistrictId, evaluation state. Обзор и Planner получают props по контракту. Собственный App Router `/` остаётся оболочкой.
3. Подключи импорт tokens/globals из Claude 1 в layout, примитивы и CityOverview; затем Planner и validateDraft из Claude 2. Пока модулей нет, используй временную простую заглушку только в своей области, без копии чужой реализации. Убери заглушки при интеграции.
4. Создай API client для GET /api/scenario и POST /api/simulations/evaluate: прямой browser fetch через `NEXT_PUBLIC_API_URL`, локально `http://localhost:8080`. Нормализуй завершающий слеш base URL. Нужны явная обработка статуса и JSON, AbortController, timeout, отсутствие автоматического retry POST. Относительные запросы к Next без base URL не подходят для согласованной схемы.
5. Используй актуальный корневой docs/api.md: Тамерлан уже подтвердил Swagger, POST по HTTP, CORS localhost:3000 и эталон 95 / 56.54. Сохрани/сгенерируй DTO, создай adapter, проверяющий необходимые поля ответа. Не используй безусловное `as ScenarioVM` для сырого JSON. Applied effects отсутствуют по согласованному контракту — ставь null, не блокируй интеграцию ожиданием поля.
6. Маппинг правил уже описан в backend-handoff: choicesRequired, maxMeasuresPerCategory, synergies и incompatibilities. При корректном API он позволяет сразу включить реальную оценку. Если нужные поля отсутствуют в ответе старого сервера, показывай ошибку контракта; не подменяй отсутствующие правила пустыми массивами.
7. Подготовь явный dev/test mock без автоматического fallback при сетевой ошибке. Fixture содержит полный сценарий из датасета, а не выдуманные нули. Контрольный успешный ответ желательно взять из реального C# после проверки эталона. Static fixture результата не является алгоритмом расчёта и не должен принимать произвольные choices как будто посчитал их.
8. Отправляй choices ровно по API. City-мере districtId не добавляется вообще; district-мера должна иметь валидный ID. Не передавай UI-only поля. Проверь validateDraft перед отправкой, затем всегда доверяй окончательному решению сервера.
9. Фиксируй снимок choices и request ID на submit; блокируй редактирование. После отмены/сброса/нового revision игнорируй поздний ответ. Ошибки не сбрасывают набор.
10. Реализуй Results: Score до/после, spent/remaining, пять районов, десять показателей, appliedSynergies и все поля explanation. Для display-only дельт можно вычитать `score - baselineScore`, `scoreAfter - scoreBefore`, `indicatorsAfter[id] - indicatorsBefore[id]`; это разрешено владельцем API. Не пересчитывай формулу Score, лаги или эффекты мер. `appliedEffects: null`: соответствующий раздел скрыт. После изменения набора результат становится неактуальным.
11. Показывай explanation как текст. Не вызывай LLM, не добавляй API key и не рассчитывай Score в Next. По handoff при сбое live LLM сервер возвращает mock-объяснение без потери чисел. Backend LLM_MODE=mock работает через настоящий API; frontend не должен включать собственные fixtures при сбое LLM.
12. Сохрани согласованную прямую схему подключения: NEXT_PUBLIC_API_URL передаётся на build и встраивается в браузерный код. При смене адреса нужна пересборка. Next rewrites и API_INTERNAL_URL не добавляй; внутренний Docker hostname не используется браузером. Проверь production-сборку в целевом окружении.
