# Задание GPT — API, состояние, результаты и сборка

Передайте этот файл аккаунту GPT целиком. Рабочий проект — репозиторий BAITC-Hacks/hack-4c816c70-team, каталог `frontend/`.

Ты интегратор фронтенда. Прочитай `AGENTS.md`, все четыре основных документа в `docs/`, `docs/backend-handoff.md`, `lib/contracts/ui.ts` и корневой `../docs/api.md`. Собери приложение из модулей двух Claude и своих модулей, сохранив текущий Next.js App Router.

## Твоя область

`app/`, `features/simulator/`, `features/results/`, `lib/api/`, `lib/contracts/`, `lib/format/`, `mocks/`, `tests/`, `package.json`, lockfile, конфигурация фронта, frontend README, `docs/reports/gpt.md`. Ты единственный редактор зависимостей. Не меняй файлы Claude, backend, корневой docs/api.md, compose, корневой README и THIRD_PARTY; замечания передавай владельцам.

Общий `lib/contracts/ui.ts` уже задан. Не изменяй его несовместимо без уведомления обоих Claude. DTO/API типы размещай отдельно. Не превращай внутренний UI-contract в выдуманный Swagger.

## Порядок реализации

1. Проверь npm ci, текущие lint и build. Добавь typecheck script с генерацией Next types при необходимости. Сохрани установленный стек; не обновляй версии ради обновления.
2. Подготовь Simulator: единый reducer, active step, scenario load state, choices, selectedDistrictId, evaluation state. Обзор и Planner получают props по контракту. Собственный App Router `/` остаётся оболочкой.
3. Подключи импорт tokens/globals из Claude 1 в layout, примитивы и CityOverview; затем Planner и validateDraft из Claude 2. Пока модулей нет, используй временную простую заглушку только в своей области, без копии чужой реализации. Убери заглушки при интеграции.
4. Создай API client для GET /api/scenario и POST /api/simulations/evaluate. Relative /api paths, явная обработка статуса и JSON, AbortController, timeout, отсутствие автоматического retry POST.
5. Сверь live Swagger с корневым docs/api.md из `8117017`: endpoints уже реализованы командой. Сохрани/сгенерируй DTO, создай adapter, проверяющий необходимые поля ответа. Не используй безусловное `as ScenarioVM` для сырого JSON. Оставшиеся пробелы — applied effects и отдельные числовые дельты — перечислены в backend-handoff.
6. Маппинг правил уже описан в backend-handoff: choicesRequired, maxMeasuresPerCategory, synergies и incompatibilities. При корректном API он позволяет сразу включить реальную оценку. Если нужные поля отсутствуют в ответе старого сервера, показывай ошибку контракта; не подменяй отсутствующие правила пустыми массивами.
7. Подготовь явный dev/test mock без автоматического fallback при сетевой ошибке. Fixture содержит полный сценарий из датасета, а не выдуманные нули. Контрольный успешный ответ желательно взять из реального C# после проверки эталона. Static fixture результата не является алгоритмом расчёта и не должен принимать произвольные choices как будто посчитал их.
8. Отправляй choices ровно по API. City-мере districtId не добавляется вообще; district-мера должна иметь валидный ID. Не передавай UI-only поля. Проверь validateDraft перед отправкой, затем всегда доверяй окончательному решению сервера.
9. Фиксируй снимок choices и request ID на submit; блокируй редактирование. После отмены/сброса/нового revision игнорируй поздний ответ. Ошибки не сбрасывают набор.
10. Реализуй Results: Score до/после, spent/remaining, пять районов, десять показателей, applied effects/synergies и все поля explanation. Если API не отдаёт дельту, сначала показывай пару чисел без собственного прогноза. После изменения набора результат становится неактуальным.
11. Показывай explanation как текст. Не вызывай LLM, не добавляй API key и не рассчитывай Score в Next. Backend LLM_MODE=mock работает через настоящий API.
12. Настрой rewrites/согласуй reverse proxy с владельцем сервера. Внутренний Docker hostname не используется браузером. Укажи влияние build-time env на rewrites и проверь production-сборку в целевом окружении.

## Проверки

Добавь только необходимые инструменты: runner для meaningful unit tests и Playwright для основного browser flow, если они доступны команде. Зафиксируй версии lockfile. Claude 2 пишет тесты validateDraft; ты обеспечиваешь их запуск.

Проверь payload городской меры, обработку API errors, stale response, изменение набора после результата. Пройди контрольный сценарий с реальным C#: 52,56 -> около 56,54, расходы 95, остаток 5. Проверь серверный отказ при перерасходе и несовместимости прямым запросом в обход UI, затем корректное отображение таких ошибок в интерфейсе.

В браузере проверь 1440×900, 768×1024 и 390×844, focus, reduced motion, отсутствие горизонтального переполнения и console errors. Передай Claude 1/2 конкретные дефекты их модулей; не переписывай их целиком.

## Передача архитектору и серверу

Отчёт `docs/reports/gpt.md`: commits модулей, фактические команды и результаты, screenshots, API URL и версия контракта, блокеры, список новых пакетов/ассетов для THIRD_PARTY, требования к proxy/env. Не объявляй приложение готовым по одному build: нужен реальный API и контрольный сценарий.

Интегрируй commits по одному из отдельных веток/клонов. Не делай force push и не переключай ветку в общем каталоге, где другой аккаунт редактирует файлы. Сохраняй промежуточную работу не реже 30 минут. Финальную compose-проверку по README проводит владелец сервера; передай ему воспроизводимые ошибки.
