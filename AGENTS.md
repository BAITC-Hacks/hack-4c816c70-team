# Правила агентов в репозитории

## Git-идентичность участника

Git-операции выполняются от аккаунта участника, который поручил задачу. Его явное указание в текущей сессии имеет приоритет; общие инструкции репозитория не должны навязывать всем участникам один аккаунт.

В сессиях Hizeshi автор и аккаунт push — Hizeshi. Независимые участники команды (включая Тамерлана/TamerlanWebd и DevOps) коммитят и публикуют собственную работу от своих аккаунтов. Не требовать от них учётные данные Hizeshi, не блокировать их push и не переписывать их авторство. Запрет искусственной AI-атрибуции сохраняется.

- Author и committer должны соответствовать участнику, от имени которого работает агент.
- Перед push проверить `gh api user --jq .login` и соответствие аккаунту текущего пользователя. Не переключаться на аккаунт другого участника команды без его явного поручения.
- Перед commit проверить `git var GIT_AUTHOR_IDENT` и `git var GIT_COMMITTER_IDENT`. Оба должны соответствовать текущему пользователю. В отдельном клоне/worktree настроить локальную Git-конфигурацию; не считать, что она переносится из этого каталога.
- Не использовать Codex, Claude, OpenAI, Anthropic или других AI-агентов в качестве автора/коммитера. Не добавлять AI `Co-authored-by`, `Signed-off-by`, `Generated by` и рекламные подписи инструментов в сообщения коммитов и описания PR.
- Не добавлять AI-атрибуцию автоматически через commit template, hooks или переменные `GIT_AUTHOR_*`/`GIT_COMMITTER_*`. Проверять полный текст нового коммита перед push.
- Обычные технические упоминания реальных зависимостей и сервисов в коде и документации не являются подписью автора и сохраняются, когда нужны для достоверности.
- Не подменять авторство коммитов других участников команды. Опубликованную историю не переписывать и force push не выполнять без отдельного прямого запроса пользователя.

## Проверка новых коммитов перед отправкой

В каждой рабочей копии один раз включи версионируемые hooks: `git config --local core.hooksPath .githooks`. Это локальная настройка: обычный clone не включает hooks автоматически.

Hooks проверяют author/committer и AI-подписи при создании и отправке новых коммитов, включая merge-коммиты. Обычные технические упоминания используемых сервисов разрешены. При блокировке исправь собственный неопубликованный коммит; не обходи проверку через `--no-verify`. Опубликованную историю и авторство других участников сохраняй. Авторизацию push проверяй отдельно через `gh api user --jq .login`: hooks не меняют аккаунты.

В общей рабочей копии Git-операции выполняет один интегратор, чтобы параллельные агенты не смешивали изменения. Прямое поручение пользователя текущему агенту имеет приоритет. Перед commit просматривать diff и добавлять только файлы своего завершённого задания; не включать незавершённую работу других агентов.

Правила разработки фронтенда и текущие задания находятся в `frontend/AGENTS.md` и `frontend/docs/tasks/`.

## Обязательная синхронизация с командой

- В начале задания, перед интеграцией, перед commit/push и перед деплоем выполнить `git fetch origin`, проверить `git status -sb` и новые commits/diff относительно origin/main.
- При длительной работе проверять origin на контрольных точках не реже раза в 15 минут. Это обязанность выполняющего задачу агента, не обещание фонового мониторинга после завершения сессии.
- Если рабочая копия чистая и ветка только отстаёт, выполнить `git pull --ff-only`. Не продолжать работу на старом контракте API после его обновления.
- Если есть незавершённые изменения или одновременно работают другие агенты, сначала согласовать интеграцию с единственным Git-интегратором. Не делать автоматический pull/rebase/stash поверх чужой работы. Сохранить завершённые собственные изменения отдельно и объединить историю без их потери.
- При расхождении истории проверить входящие изменения, выполнить обычное слияние после сохранения своей работы и разрешить конфликты; не использовать force push, reset --hard или очистку рабочей копии ради синхронизации.
- После получения новой версии повторить проверки затронутой части. Перед серверным обновлением зафиксировать точный SHA; не собирать релиз из случайного текущего состояния общей папки.
- Проверенный промежуточный commit/push не реже часа. Следить отдельно за локальным commit, опубликованным SHA и реально запущенным на сервере SHA.
